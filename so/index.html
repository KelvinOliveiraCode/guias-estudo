MÓDULO 0 · AULA 01

O que é um Sistema Operacional O que é um Sistema Operacional, por que ele existe, e como ele nasceu em quatro gerações

A situação-problema que funda tudo

O ponto de partida: uma máquina só com hardware — processador, memórias RAM, disco, sem nenhum software instalado. A tarefa: escrever um programa em Java que leia um arquivo de texto desse disco e o imprima numa impressora USB. Sem um Sistema Operacional, o próprio programa teria que controlar cada dispositivo — drivers, interrupções, temporização. É esse trabalho que o SO assume.

A questão

Como o seu código Java vai dizer para a CPU: rotacionar o motor físico do disco? Posicionar a agulha de leitura no cilindro magnético certo? Acionar os pulsos elétricos da porta USB da impressora? — e se não houver um SO entre o código e o hardware?

A resposta é o próprio motivo de a disciplina existir: sem o SO, cada programador do mundo teria que ser engenheiro de hardware e programar o comportamento elétrico de cada pino da placa-mãe. Seria o caos completo.

O que é um Sistema Operacional (definição que cai na prova)

Definição formal

Um Sistema Operacional é um programa que gerencia o hardware de um computador, servindo de intermediário e elo entre o usuário e o hardware físico.

O SO tem uma dupla personalidade, descrita por duas visões clássicas. Essa é a pergunta mais comum de prova conceitual sobre SO — decore os dois focos.

Frase de prova

“O SO abstrai a complexidade do hardware para o usuário” (visão do usuário) e aloca de forma justa e protegida os recursos de hardware (visão do sistema).

As camadas do sistema: por que seu programa não toca no hardware

Seus aplicativos executam num ambiente com privilégios limitados. Para alcançar a física, eles precisam bater na porta do Kernel — é a System Call.

O que isso evita na prática

É exatamente isso que impede que uma aba travada do navegador destrua ou apague o seu sistema inteiro. Se tudo rodasse com o mesmo privilégio, um bug em uma única aba derrubaria o computador — e com ele, todos os seus arquivos.

Evolução histórica: da válvula ao seu smartphone

Os SOs não surgiram prontos. Cada geração nasceu de um problema prático da anterior.

1ª
1945 – 1955 · Válvulas e Painéis de Fiação
Sem Sistema Operacional. Programação direta em linguagem de máquina por meio de plugues, chaves elétricas e cartões perfurados. Um único usuário monopolizava a sala inteira da máquina por horas para cálculos de trajetórias balísticas (ENIAC). Queria mudar a programação? Entrava fisicamente e refazia a fiação de chaves e relés.
2ª
1955 – 1965 · Transistores e Sistemas em Lote (Batch)
Nasce o transistor e as primeiras linguagens (Assembly e Fortran). Surge o Sistema Batch, otimizando a CPU: o operador agrupava cartões perfurados em fitas magnéticas e o computador processava uma tarefa de cada vez, sequencialmente, via Monitor Residente. Para não desperdiçar a CPU esperando o operador trocar cartões, as tarefas ficavam gravadas em fita e rodavam uma atrás da outra.
3ª
1965 – 1980 · Circuitos Integrados e o Nascimento da Multitarefa
Multiprogramação: vários processos residem na RAM ao mesmo tempo. Se o Job A espera a leitura de uma fita (operação de E/S), a CPU não fica ociosa — muda de contexto imediatamente e executa o Job B. Tempo Compartilhado (Timesharing): divisão de pequenos intervalos (fatias de tempo) entre dezenas de usuários em terminais burros, criando a sensação de máquina exclusiva para cada um.
4ª
1980 – Hoje · Microprocessadores e Interfaces Gráficas
Invenção do microchip de silício e dos PCs acessíveis. Evolução do MS-DOS e do UNIX clássico para sistemas modernos com GUI (Windows, macOS, Linux). Surgem SOs de Rede (máquinas trocando pacotes) e Sistemas Distribuídos (processamento transparente compartilhado). O computador migrou do laboratório para as nossas casas.
O grande salto: por que a multiprogramação mudou tudo

Antes, se um programa demorasse 10 minutos para ler um disco lento, o processador — que opera na escala de nanossegundos — ficava completamente parado, ocioso, desperdiçando energia elétrica. Com a multiprogramação, o SO passou a manter vários programas na RAM e a chavear a CPU entre eles conforme necessário. Até hoje, multiprogramação e timesharing governam os SOs modernos — do seu smartphone ao servidor em nuvem.

MÓDULO 1 · AULA 02

Anatomia do SO: Kernel e a Linha de Fronteira Como o processador impede que um programa malicioso destrua o seu sistema

A situação-problema: o aplicativo malicioso

Um discente do IFPA desenvolveu um jogo em Java. Ele roda perfeitamente — mas contém um bug sutil, ou, pior, um trecho de código malicioso oculto. Ao ser executado, o programa tenta:

  • Acessar diretamente a tabela de processos na memória para encerrar o antivírus.
  • Enviar comandos diretos de gravação nos setores físicos do disco para apagar dados de outros usuários.
Se qualquer programa de usuário pudesse tocar no hardware sem restrição…

Como impedir que uma aplicação trave a CPU em um laço infinito? Como evitar que ela corrompa todo o sistema de arquivos? Como o processador e o SO cooperam para isolar e proteger as aplicações umas das outras?

O bit de modalidade: a proteção é feita no hardware

O SO não confia em si mesmo por educação — a proteção é imposta pelo processador através de um único bit físico chamado Mode Bit.

Modo Kernel — Bit = 0

Modo supervisor / privilegiado.

Permite instruções privilegiadas: acesso irrestrito ao hardware, controle de E/S, gerenciamento de interrupções e dos registros base/limite.

Modo Usuário — Bit = 1

Conjunto de instruções limitado.

Qualquer tentativa de executar instrução privilegiada gera uma trap por instrução ilegal, transferindo o controle ao SO.

O ciclo de vida da modalidade

1
Inicialização

O computador inicializa sempre em Modo Kernel, para carregar o SO com privilégio total.

2
Execução de aplicações

Ao rodar um programa de usuário, o hardware muda o bit para 1 (Modo Usuário).

3
Interrupção / System Call

Qualquer interrupção, exceção ou chamada de sistema muda o bit para 0 (Modo Kernel).

Chamadas de Sistema (System Calls)

Definição

Representam a interface formal que um programa em execução utiliza para solicitar serviços do SO. São a única forma legítima de cruzar a fronteira de segurança.

Escrever chamadas de sistema direto em assembly é complexo, então os desenvolvedores usam APIs padronizadas: POSIX (Linux e macOS) e Win32 / Win64 (Windows).

Como os parâmetros chegam ao SO — três métodos clássicos

MétodoComo funcionaPrós e contras
RegistradoresParâmetros enviados direto nos registradores da CPU. Rápido, porém limitado pela quantidade de registradores do processador.
Tabela na MemóriaParâmetros gravados num bloco de memória; o endereço do bloco é passado em um registrador. Sem limite de tamanho, porém custa uma leitura extra de memória.
Pilha (Stack)Parâmetros inseridos na pilha do processo de usuário e desempilhados pelo kernel. Organizado e flexível; é o mais comum em arquiteturas modernas.

Os seis tipos de System Calls

Controle de Processos

Criar/encerrar processos (fork(), exit()), alocar memória.

Gerenciamento de Arquivos

Criar, ler, gravar, fechar e excluir (open(), read(), write(), close()).

Gerenciamento de Dispositivos

Solicitar e liberar dispositivos de hardware (drivers de E/S).

Manutenção de Informações

Obter hora, data e atributos do sistema (time(), date()).

Comunicações

Criar/excluir conexões, enviar e receber mensagens entre processos via IPC.

Proteção

Definir e obter permissões de recursos e controle de acesso (chmod()).

Classificação conforme Silberschatz, Galvin & Gagne — Fundamentos de Sistemas Operacionais, 9ª ed.

Estruturas de SO: como o kernel é organizado

Monolítico — “A Grande Bagunça”

O kernel inteiro é escrito como um binário monolítico único. Todo o código (drivers, escalonador, rede) reside em um único espaço de endereçamento de memória.

Vantagem

Desempenho máximo — sem overhead de comunicação interna. Tudo ocorre por chamadas de funções baratas em C.

Desvantagem

Difícil manutenção e fragilidade física: se um driver de vídeo falhar, o kernel inteiro cai. Exemplos: MS-DOS, Linux original.

Em Camadas — Modularidade

O SO é dividido em níveis hierárquicos — da Camada 0 (junto ao hardware) até a Camada N (junto ao usuário). Cada camada só pode invocar serviços das camadas diretamente inferiores.

Vantagem

Alta modularidade e facilidade de depuração — cada camada pode ser testada e verificada de forma isolada.

Desvantagem

Menor eficiência — overhead alto para atravessar múltiplas camadas de parâmetros a cada chamada de serviço.

Microkernels — O Kernel Minimalista

Conceito presente no Mach e no MINIX. A ideia é modularizar removendo do kernel todos os componentes não essenciais e movendo-os para o Espaço do Usuário, na forma de processos servidores (servidor de arquivos, servidor de processos…).

O kernel mínimo fornece apenas: gerenciamento mínimo de processos e memória, mecanismos de comunicação entre processos (IPC) e mecanismo de mensagens. A comunicação entre clientes e servidores é feita por troca de mensagens gerenciada pelo Microkernel.

Vantagens

Confiabilidade: se o servidor de arquivos falhar por um bug, o resto do SO continua funcionando normalmente.

Extensibilidade e portabilidade: novos serviços são criados no espaço de usuário sem alterar o kernel.

Desvantagem

Queda de desempenho expressiva devido ao overhead constante de cópia e troca de mensagens entre as fronteiras do sistema.

LKMs e Arquiteturas Híbridas

Os Módulos Carregáveis do Kernel (LKMs) são a abordagem moderna adotada pelo Linux para manter alto desempenho com modularidade flexível:

1
Kernel Básico Essencial

Contém apenas as estruturas fundamentais do SO, mantendo o núcleo enxuto.

2
Módulos Dinâmicos

Drivers, protocolos de rede e sistemas de arquivos são escritos como módulos carregados e descarregados sob demanda.

3
Sem Overhead de Mensagens

Diferente do microkernel, os LKMs rodam dentro do espaço de kernel, com privilégio máximo.

Sistemas Híbridos (macOS / Windows)

Combinam a velocidade dos monolíticos com o isolamento dos microkernels.

M
macOS (Darwin)

Arquitetura híbrida: microkernel Mach com componentes monolíticos do BSD no mesmo espaço de kernel.

N
Windows NT

Kernel híbrido que combina um microkernel com serviços de sistema rodando em modo kernel para alto desempenho.

Para a aula de casa desta aula

Leia o Capítulo 2 do Silberschatz. No terminal do Linux, execute strace ls e observe as System Calls que um simples comando dispara — cada linha é uma batida na porta do Kernel.

MÓDULO 2 · AULA 03

Processos: Programa em Execução Programa vs. processo, anatomia na RAM, os 5 estados, o PCB e o custo invisível da troca de contexto

Programa vs. processo: a diferença que importa

Programa × processo — o mesmo código em dois estados
O Programa (estático)

É o arquivo no disco (.exe, .class). Fica passivo no armazenamento (HD ou SSD) sem consumir CPU nem RAM e não faz nada sozinho.

O Processo (dinâmico)

É o programa carregado e em execução: a CPU processa suas instruções em tempo real e ele ocupa memória, PID e estado próprios.

Entradas e Saídas

Dados de entrada (inputs) → processamento → resultado (output)

Interrupção e retomada

Um evento urgente chega. O SO: (1) salva o estado do processo, (2) atende a urgência e (3) retoma exatamente do ponto em que parou.

O conceito central

É exatamente isso que o escalonador faz: salvar o estado para atender algo mais urgente e depois restaurar o processo exatamente de onde parou. É o conceito de troca de contexto, que você vê em detalhe mais abaixo.

Anatomia de um processo na memória RAM

O ciclo de vida: os 5 estados de um processo

Novo (New)

Em fase de criação e alocação de recursos pelo SO.

▶️ Em Execução

As instruções estão sendo ativamente processadas pelos núcleos da CPU.

⏹ Terminado

Encerrou a execução; seus recursos na RAM serão liberados pelo SO.

⏸ Em Espera / Bloqueado

Pausado aguardando um evento externo (conclusão de leitura em disco, entrada do teclado).

Pronto (Ready)

Apto para rodar, esperando que o escalonador o selecione para ocupar a CPU.

A diferença que mais cai em prova

Em espera ≠ Pronto. O processo Bloqueado espera algo que nem ele pode resolver (o disco terminar de ler) — a iniciativa é de fora. O processo Pronto espera algo que depende só do SO — a CPU ficar livre. Só o escalonador decide quem sai do Pronto.

O “RG” do processo: o Bloco de Controle de Processo (PCB)

Como o Kernel gerencia centenas de processos concorrentes? Cada processo possui uma estrutura de dados de controle — o PCB (Process Control Block), também chamado de tabela de processos. É o documento de identidade do processo no Kernel.

Informação no PCBO que guardaPara que serve
Estado AtualNovo, pronto, executando, bloqueado ou terminadoSaber em que fase o processo está
PIDIdentificador numérico exclusivoDistinguir um processo de outro
Contador de Programa (PC)Endereço da próxima instrução a executarRetomar exatamente de onde parou
Registradores da CPUCópia dos acumuladores e de uso geralGuardados no momento em que o processo perde o processador
Limites de MemóriaRegistadores base e limiteProteger a RAM e impedir que um processo invada a memória do outro
Status de I/OLista de arquivos abertos e dispositivos alocadosSaber o que o processo tem em uso

A engenharia por trás da troca de contexto

O Context Switch é como o computador simula multitarefa criando o que chamamos de pseudoparalelismo.

1
SO Suspende

Suspende o processo em execução por fim do tempo ou por interrupção de hardware.

2
Salva o Estado

O Kernel salva o estado atual da CPU no PCB do processo que sai.

3
Restaura o Estado

Restaura o estado salvo a partir do PCB do novo processo selecionado.

4
CPU Retoma

A CPU retoma o novo processo exatamente do ponto onde tinha parado.

O custo invisível: o Overhead

Esse chaveamento físico de registradores e mapa de memória é oneroso. Durante esses microssegundos, o processador não executa nenhum código útil do usuário — consome processamento apenas com a administração interna do Kernel.

Multiprogramação

Executar Spotify e a IDE simultaneamente é um chaveamento ultrarrápido que cria a ilusão de paralelismo.

Puro Overhead

Durante a troca, a CPU não processa apps do usuário — apenas gerencia o estado interno do Kernel.

MÓDULO 3 · AULA 04

Escalonamento de CPU: Escolhendo o Próximo Processo O ciclo de picos, as métricas de avaliação e os quatro algoritmos com Gantt e contas feitas

A situação-problema: qual processo usa a CPU agora?

Três processos na fila de prontos, um só CPU
P₁ — CPU-bound

Surto longo
Tempo de CPU: 25 ms

P₂ — I/O-bound

Surto curto
Tempo de CPU: 1 ms

P₃ — I/O-bound

Surto médio
Tempo de CPU: 3 ms

FCFS: P₁ chegou primeiro — P₂ espera 25 ms com um surto de 1 ms. Justo?
SJF: Menor surto à frente reduz a espera média, mas P₁ pode nunca ser atendido (Starvation!).

A questão: como o SO decide, em tempo real, qual processo assume a CPU de forma eficiente, justa e sem travar o sistema?

O ciclo de vida dos processos: CPU Burst e I/O Burst

A execução de qualquer processo consiste em um ciclo alternado de duas atividades: processamento ativo (CPU burst) e espera por dispositivos (I/O burst).

Tipos de processos

CPU-bound

Picos longos e raros.
Exemplos: algoritmos de IA, renderizadores de vídeo.

I/O-bound

Picos curtos e frequentes.
Exemplos: editores de texto, navegadores, IDEs.

A regra do escalonador

O escalonador deve selecionar um bom mix de processos para manter a CPU e os controladores de E/S sempre ocupados de forma concorrente. Só com I/O-bound a CPU fica ociosa; só com CPU-bound os discos ficam parados.

Métricas de avaliação de escalonadores

MétricaObjetivoDefinição
Utilização da CPUMaximizarMeta: 40% (carga leve) a 90% (alto desempenho)
Throughput / VazãoMaximizarProcessos concluídos com sucesso por unidade de tempo
Tempo de TurnaroundMinimizarSubmissão até conclusão = CPU Burst + Espera + E/S
Tempo de EsperaMinimizarSoma dos períodos aguardando passivamente na fila de prontos
Tempo de RespostaMinimizarRequisição até a primeira resposta visível — essencial para sistemas interativos
Não confunda as duas últimas

Turnaround vai da submissão até o processo terminar. Resposta vai da requisição até o usuário ver o primeiro resultado. Em um sistema interativo, importa mais a resposta; em um sistema de lote, importa mais o turnaround.

Algoritmo 1 — FCFS / FIFO

O primeiro processo que solicita a CPU é o primeiro a ser executado, implementado por uma fila linear simples FIFO. É não-preemptivo: o processo permanece na CPU até terminar voluntariamente ou solicitar E/S.

O grande gargalo: Efeito Comboio (Convoy Effect)

Ocorre quando processos curtos (I/O-bound) ficam bloqueados aguardando um único processo gigantesco (CPU-bound) que domina o processador. Resulta em: baixa utilização dos dispositivos de E/S, latência média de espera inaceitável e alta dependência da ordem de chegada dos processos.

Exemplo resolvido 1 — FCFS com os 4 processos prontos em t = 0

TT médio = (20 + 25 + 32 + 34) / 4 = 27,75 ms

Exemplo resolvido 2 — os MESMOS processos, mas com P₂ chegando primeiro

Mesmos 4 processos e os mesmos surtos de CPU. A única mudança é a ordem de chegada: P₂, P₃, P₄ e só depois P₁. Repare como os tempos médios caem — isso é o Efeito Comboio na prática.

Lição que a banca gosta de cobrar

Com os mesmos processos e os mesmos tempos de CPU, só a ordem de chegada mudou e a espera média caiu pela metade. Isso prova que o FCFS é pré-histórico e não justo — a alta dependência da ordem de chegada é exatamente o Efeito Comboio.

Algoritmo 2 — SJF (Shortest Job First)

Asocia a cada processo a duração do seu próximo pico de CPU. Quando o processador fica livre, aloca ao processo com o menor surto restante. É provado matematicamente que o SJF fornece o tempo médio de espera mínimo para qualquer conjunto de processos.

Previsão do futuro: a média exponencial

Como o Kernel sabe a duração do próximo pico se ainda não aconteceu? Ele estima:

Fórmula da média exponencial

τn+1 = α · tn + (1 − α) · τn

τ = estimativa · t = tempo real do pico anterior · α = peso do passado recente

Exemplo com α = 0,5 (o mais usado em aula) pico real t = 10  →  τ' = 0,5(10) + 0,5(10) = 10
pico real t = 6   →  τ' = 0,5(6) + 0,5(10) = 8
pico real t = 4   →  τ' = 0,5(4) + 0,5(8) = 6
pico real t = 6   →  τ' = 0,5(6) + 0,5(6) = 6
pico real t = 4   →  τ' = 0,5(4) + 0,5(6) = 5
pico real t = 13 → τ' = 0,5(13) + 0,5(5) = 9

Repare no exemplo: quando o pico real salta de 4 para 13, a estimativa τ só sobe suavemente de 5 até 12 — o Kernel não “acredita” num pico isolado.

Não-Preemptiva

O processo em execução conclui seu surto mesmo se chegar um novo processo mais curto.

Preemptiva — SRTF

Se um novo processo chega com surto restante menor que o atual, interrompe imediatamente e escala o novo.
Risco: processos longos podem sofrer Starvation.

Algoritmo 3 — Escalonamento por Prioridades

Cada processo recebe um valor inteiro de prioridade. A CPU é alocada ao processo de maior prioridade — por convenção, números menores = maior privilégio.

Inversão de Prioridades

Um processo de prioridade média bloqueia um de alta prioridade que aguarda um recurso retido por um de baixa prioridade.

Inanição (Starvation)

Processos de baixa prioridade podem esperar indefinidamente.
A lenda do MIT: um processo enviado em 1967 nunca executou até o IBM 7094 ser desligado em 1973!

Envelhecimento (Aging)

Aumenta gradualmente a prioridade dos processos conforme o tempo acumulado na fila de prontos — a cura para a Starvation.

Algoritmo 4 — Round-Robin (RR)

Projetado para sistemas interativos — é o algoritmo mais utilizado em sistemas multiusuário e de tempo compartilhado. Trata a fila de prontos como uma fila circular FIFO preemptiva. Cada processo recebe um quantum de tempo (q) — geralmente 10 a 100 ms — antes de ser colocado de volta no fim da fila.

Regra prática

~80% dos picos de CPU reais devem ser menores que o quantum escolhido.

A sensibilidade do quantum — o que acontece nos dois extremos

q muito grande

O RR perde sua natureza interativa e se comporta exatamente como um FCFS sequencial. Ninguém sente falta de resposta, porque ninguém é interrompido.

q muito pequeno

Número absurdo de trocas de contexto. O processador gasta mais tempo com overhead de Kernel do que processando código útil.

Threads e Concorrência: Execução Concorrente O que é uma thread, o que elas compartilham, e a condição de corrida que faz contas bancárias falharem

A situação-problema: o navegador congelado

Três tarefas pesadas rodando ao mesmo tempo
Tarefa 1

Videoaula de programação
Reprodução contínua de vídeo em streaming de alta definição.

Tarefa 2

PDF de 50 MB
Download e renderização de relatório acadêmico de grande volume.

Tarefa 3

Script de animação
Processamento gráfico pesado rodando em loop contínuo.

O problema: se o navegador funcionasse com execução single-thread, um travamento na animação congelaria toda a interface — inclusive o vídeo e o mouse. A questão: como o navegador moderno carrega páginas, roda scripts, reproduz áudio/vídeo e responde a cliques de forma simultânea sem que um travamento pontual congele tudo?

Mas afinal, o que é uma thread?

Definição formal

Uma thread (ou fluxo de controle) é a unidade básica de utilização da CPU. Representa um caminho de execução independente de instruções dentro de um processo.

O conceito por trás é o de Processo Leve (Lightweight Process): diferente de um processo tradicional (heavyweight), que é pesado para criar e destruir, a thread é extremamente leve porque não precisa de um espaço de endereçamento totalmente novo. Um processo multithreaded contém vários fluxos de execução cooperativos dentro do mesmo espaço de memória.

O que as threads dividem e o que elas isolam

Recursos Compartilhados

Seção de Código — todas as threads leem as mesmas funções.

Seção de Dados (globais) — se uma altera uma global, todas as outras enxergam imediatamente.

Recursos do SO — arquivos abertos, sockets de rede e permissões.

Memória Heap — área de alocação dinâmica (objetos com new em Java).

Recursos Privados (de cada thread)

ID da Thread — identificador único no sistema.

Contador de Programa (PC) — qual instrução aquela thread está executando.

Conjunto de Registradores da CPU — valores de cálculo temporários da thread.

Memória Stack (Pilha) — variáveis locais e histórico de chamadas de métodos.

Por que isso importa para a prova

É exatamente porque código e dados são compartilhados que duas threads podem atacar o mesmo recurso ao mesmo tempo — e é por isso que a Região Crítica (Módulo 5) precisa existir. A pilha e os registradores serem privados é o que garante que uma thread não embaralhe a execução da outra.

Os quatro pilares de benefício das threads

1
Capacidade de Resposta

A aplicação continua respondendo ao usuário mesmo se parte dela estiver bloqueada em operação demorada (ex.: baixando um arquivo).

2
Compartilhamento de Recursos

Threads compartilham a memória do processo por padrão, facilitando troca de dados sem mecanismos complexos de IPC (pipes, memória compartilhada explícita).

3
Economia de Hardware

Criar e gerenciar threads é muito mais rápido e consome menos memória que criar processos.

4
Escalabilidade (Multicore)

Em sistemas multiprocessadores, threads independentes podem executar em paralelo em diferentes núcleos simultaneamente.

Concorrência versus Paralelismo

Concorrência (Concurrency)

Existência de múltiplas tarefas que dão a ilusão de execução simultânea. Em uma CPU de núcleo único, o escalonador faz o chaveamento rápido no tempo entre os fluxos. Apenas um fluxo executa por vez.

Paralelismo (Parallelism)

Execução física e simultânea de duas ou mais tarefas ao mesmo tempo. Exige, obrigatoriamente, hardware com múltiplos núcleos (multicore). As tarefas realmente executam ao mesmo tempo.

A frase que separa os dois concepts

Concorrência é uma questão de estrutura (como o programa é organizado). Paralelismo é uma questão de hardware (quantos núcleos existem). Um sistema pode ser concorrente sem ser paralelo — é o caso do seu notebook com 1 núcleo.

Os três desafios da era multicore

  1. Identificação de tarefas independentes — encontrar quais partes do problema podem ser divididas e executadas sem dependência entre si.
  2. Equilíbrio de carga e divisão de dados — distribuir o trabalho e os dados de forma justa entre os núcleos disponíveis.
  3. Sincronização e depuração — gerenciar dependências entre dados e lidar com a complexidade de testes e depuração de sistemas concorrentes.

Quem gerencia as threads? Usuário vs. Kernel

Threads de Nível de Usuário

Gerenciamento por biblioteca — criadas e gerenciadas inteiramente por bibliotecas no espaço de usuário (ex.: Java Threads).

Rápidas de criar, sem chamadas de sistema.

⚠️ O calcanhar de Aquiles: se uma única thread de usuário fizer uma chamada bloqueadora ao SO (como ler do disco), o processo inteiro é pausado.

Threads de Nível de Kernel

Gerenciamento pelo SO — o núcleo reconhece e gerencia as threads diretamente. Se uma thread bloqueia, o SO agenda outra do mesmo processo.

Suporte nativo a multicore.

⚠️ Maior custo de criação (cada uma é uma syscall).

Os três modelos clássicos de mapeamento

Muitos-para-Um

Várias threads de usuário → 1 thread de kernel.

Um-para-Um

Cada thread de usuário ganha uma de kernel (Windows e Linux).

Muitos-para-Muitos

Multiplexa M threads de usuário em N threads de kernel (M ≥ N).

O perigo da concorrência: a Condição de Corrida

Race Condition (Condição de Corrida)

Uma situação onde múltiplos fluxos de execução (threads ou processos cooperativos) tentam acessar e modificar um recurso compartilhado de forma simultânea, e o resultado final depende estritamente da ordem e do tempo de execução das instruções.

O resultado é imprevisível e inconsistente — o mesmo programa pode gerar respostas diferentes a cada execução.

O clássico exemplo da conta bancária conjunta

Thread Esposa
lê saldo = R$ 1.000,00
calcula 1.000 + 10
grava saldo = R$ 1.010,00
Thread Marido
lê saldo = R$ 1.000,00
calcula 1.000 − 10
grava saldo = R$ 990,00
Esperado vs. real

Esperado: R$ 1.000,00 (depositou 10, sacou 10 — o saldo volta ao original).
Sem sincronização: se ambas leram R$ 1.000,00 ao mesmo tempo, quem gravar por último apaga a operação do outro — saldo incorreto e inconsistente!

MÓDULO 5 · AULA 06

Sincronização e Deadlock Região crítica, semáforos, produtor-consumidor e o monstro do Deadlock

A situação-problema: o jantar dos filósofos

Dijkstra, 1965 — 5 threads, 5 recursos

Cinco threads alternam entre pensar e comer. Para comer, cada uma precisa de dois recursos (os hashis) — o da esquerda e o da direita. Pegam um recurso de cada vez; não podem pegar o da outra thread.

A crise: todas as cinco ficam famintas ao mesmo tempo. Cada uma pega o recurso à sua esquerda. Agora, cada thread tem 1 recurso e espera o da direita ficar livre — que já está com a vizinha.

A questão

As threads ficam paradas, cada uma segurando 1 recurso e esperando pelo outro eternamente? O que acontece com a CPU? Elas morrem de fome?

A anatomia da Região Crítica

Região Crítica

A parte do programa de uma thread em que ela acessa um recurso de memória compartilhado (como ler/gravar dados).

As 4 condições para uma solução correta

1
Exclusão Mútua

Duas ou mais threads jamais podem estar simultaneamente em suas regiões críticas.

2
Independência de Hardware

Nenhuma suposição sobre velocidade ou número de CPUs pode ser feita.

3
Progresso

Nenhuma thread fora da região crítica pode bloquear outras threads concorrentes.

4
Espera Limitada

Nenhuma thread deve esperar indefinidamente — sem inanição (starvation).

Soluções primitivas: Mutex vs. Spinlocks

Locks Mutex

Mecanismo mais simples: a thread adquire um lock antes de entrar na região crítica e o libera ao sair. Garante exclusão mútua sem desperdício de CPU quando implementado com bloqueio real.

Spinlocks — Espera Ocupada

Enquanto a região crítica está ocupada, a thread fica em loop contínuo testando a variável:

while (lock == 1);

Desperdiça ciclos preciosos de CPU em busy waiting.

Quando usar spinlocks?

Apenas quando o tempo de espera for extremamente curto — comum em multiprocessadores, onde a troca de contexto seria mais cara do que o giro. Em uma CPU de núcleo único, o giro é sempre errado: a outra thread precisa da CPU para liberar o lock, mas está esperando ela.

As engrenagens do Semáforo

Um semáforo contém um contador inteiro (value) e uma fila de processos suspensos (list). Foi proposto por Dijkstra (1965).

⬇️ DOWN (P) — Bloqueia / Solicita recurso
void DOWN(Semáforo S) {
  S.value--;
  if (S.value < 0) {
    // Adiciona thread em S.list
    block();  // Estado: Bloqueado
  }
}
⬆️ UP (V) — Acorda / Libera recurso
void UP(Semáforo S) {
  S.value++;
  if (S.value <= 0) {
    // Remove thread T de S.list
    wakeup(T); // Estado: Pronto
  }
}
Operação Atômica

Decrementa o valor: S.value--. Se S.value < 0, a thread é suspensa na fila e adormece (block()).

O Trunfo

A thread abre mão da CPU espontaneamente e dorme — eliminando completamente a espera ocupada!

Atomicidade Garantida

Ambas as operações são indivisíveis — o SO garante que nunca são interrompidas no meio da execução.

O problema do Produtor-Consumidor com semáforos

Um produtor gera itens, um consumidor os consome, e ambos precisam de um buffer compartilhado. Três semáforos resolvem o problema:

SemáforoValor inicialO que garante
mutex1Semáforo binário. Garante que apenas um processo mexa nos ponteiros do buffer por vez (Exclusão Mútua).
emptyNConta quantos espaços vazios existem no buffer. Inicializado com a capacidade total N.
full0Conta quantos espaços ocupados existem com itens produzidos. Inicializado em zero.
Produtor
down(&empty);   // espera espaço livre
down(&mutex);   // entra na região crítica
insere o item;
up(&mutex);     // sai da região crítica
up(&full);      // sinaliza item novo
Consumidor
down(&full);    // espera item
down(&mutex);   // entra na região crítica
remove o item;
up(&mutex);     // sai da região crítica
up(&empty);    // sinaliza espaço livre
A simetria que a banca adora perguntar

O produtor consome um espaço vazio e libera um espaço ocupado. O consumidor faz o caminho inverso. Note que mutex é sempre o mesmo para os dois — é ele que serializa o acesso aos ponteiros, e nunca fica negativo (é binário).

O Monstro do Deadlock e o Kansas de 1900

O problema real que inspirou o conceito

“Quando dois trens se aproximarem em um cruzamento, ambos devem parar completamente e nenhum dos dois deve ser posto em marcha novamente até que o outro tenha partido.”

A lógica impossível: se o trem A não pode se mover antes de B partir, e B não pode se mover antes de A partir — nenhum dos dois jamais sairá do lugar!

Definição científica de Deadlock

Um conjunto de processos está em deadlock quando cada processo do conjunto espera por um evento que só pode ser causado por outro processo do mesmo conjunto — uma espera circular sem saída.

As 4 Condições de Coffman (1971)

Para que o deadlock exista, as quatro condições abaixo devem ocorrer simultaneamente.

Grafo de Alocação de Recursos (RAG)

O RAG representa processos como círculos e recursos como quadrados. Uma seta de um processo para um recurso significa solicitação; uma seta de recurso para processo significa atribuição. Se houver um ciclo no grafo, há deadlock.

Estratégias do Kernel contra o Deadlock

1
Algoritmo do Avestruz

Fingir que nunca ocorre. Abordagem pragmática adotada pelo Windows e Linux: se a probabilidade for muito baixa, reiniciar é mais barato do que rodar prevenção em cada alocação.

2
Prevenção Ativa

Quebra estrita de uma das 4 condições de Coffman — por exemplo, exigir que todos os locks sejam solicitados sempre na mesma ordem absoluta.

3
Impedimento Dinâmico (Avoidance)

O SO analisa cada solicitação dinamicamente. O Algoritmo do Banqueiro (Dijkstra) verifica se conceder o recurso mantém o sistema em um estado seguro.

4
Detecção e Recuperação

Deixa o deadlock ocorrer, detecta-o periodicamente via busca de ciclos e se recupera matando o processo-vítima ou forçando preempção de recursos.
